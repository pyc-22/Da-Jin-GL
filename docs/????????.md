# 移动端开发前基线

## 1. 目的与范围

本基线用于冻结《打金店管理系统移动端设计开发文档》和《打金店管理系统移动端功能需求文档》进入编码前必须统一的接口、数据、权限、状态、离线和验收约束。内容以当前仓库的 Spring Boot Controller、`db/schema.sql`、管理端 API 封装和移动端 API 封装为核验依据。

本文件不替代两份产品文档，也不修改既有业务规则；未在本文件冻结的内容不得作为前后端联调依据。

## 2. 当前真实基线

### 2.1 技术与数据

| 项目 | 当前核验结果 |
|---|---|
| 后端 | Spring Boot，Controller 位于 `backend/src/main/java/com/dajin/system` |
| 移动端 | Vue 3 + Vite H5，目录为 `mobile/` |
| 管理端 | Vue 3 + Element Plus，目录为 `admin-web/` |
| 数据库 | MySQL 8.0，`db/schema.sql` 当前定义 38 张表 |
| 实时通信 | Spring WebSocket，实际路径为 `/ws` |
| 健康检查 | `GET /actuator/health` |
| 门店隔离 | 业务查询由后端从 JWT/请求上下文取得 `store_id` |

## 3. 统一角色与权限

### 3.1 角色编码

| 业务角色 | 唯一编码 | 数据范围 |
|---|---|---|
| 管理员 | `ADMIN` | 全局管理权限 |
| 店长 | `MANAGER` | 当前门店经营、库存、审批和报表 |
| 前台 | `CASHIER` | 当前门店收银、会员和交班 |
| 销售 | `SALES` | 本人会员、回访、移动开单和个人业绩 |

前端菜单只做显示控制，后端 `@RequireRoles` 是最终权限边界。任何带 `store_id` 的查询都必须由后端根据登录身份确定门店，不信任前端单独传入的门店值。

### 3.2 当前移动端底部菜单

| 角色 | 菜单键 |
|---|---|
| `MANAGER` / `ADMIN` | `dashboard`、`approval`、`report`、`member` |
| `SALES` | `members`、`visits`、`order`、`performance` |

回访键跳转现有 `/visits` 页面；消息、个人中心、库存、交班和商品详情作为二级页面访问。

## 4. 核心数据约束

### 4.1 金额、重量和日期

- 金额使用数据库 `DECIMAL`，展示统一保留 2 位小数并使用人民币符号。
- 克重统一使用克，录入精度按业务字段定义，现有商品和旧料字段最多 3 位小数。
- 成色在接口中使用 0 到 1 的小数，例如 99% 传 `0.99`；页面显示百分比。
- 生日使用 `DATE` 和 `YYYY-MM-DD`，不携带时间。
- 前端展示时间使用门店业务时区 `Asia/Shanghai`；数据库时间保存为服务端统一时间。
- 舍入规则统一为金额 `HALF_UP`，禁止页面和后端各自截断。

### 4.2 关键历史快照

- 销售订单明细使用 `sales_order_item.cost_snapshot` 计算历史成本。
- 加工订单使用项目名称、工费和提成比例快照。
- 金价、支付、库存和旧料流水必须保留来源单号、操作人和门店。
- 软禁用优先于物理删除；存在订单、审批、库存或日志关联时保留历史数据。

## 5. 状态机

### 5.1 销售订单

`待结算 -> 已完成`；折扣审批订单为 `待审批 -> 已完成` 或 `待审批 -> 已退单`。支付完成前不得扣减最终库存，重复提交必须由门店加客户端请求号幂等处理。

### 5.2 加工订单

`PENDING -> PROCESSING -> COMPLETED -> PICKED_UP`。

- 只能按顺序流转。
- `COMPLETED` 前必须满足应收已结清。
- 加工完成默认通知客户，成品直接交付，不自动进入成品库存。
- 剩余旧料选择 `TAKE_AWAY` 时不入旧料库存；选择 `STORE_DEDUCT` 时按有效克重入库并抵扣工费。

### 5.3 审批

`待审批(1) -> 已通过(3)` 或 `待审批(1) -> 已驳回(4)`。

- 驳回必须填写原因。
- 盘点审批通过时按差异写入 `stock_in` / `stock_out` 并更新商品库存。
- 折扣审批驳回时删除待激活的旧料记录，避免形成虚假库存。

### 5.4 盘点单

`待审批 -> 已通过/已驳回`。审批通过逐商品锁定库存行、计算实盘与系统差异、写库存流水；同一盘点单只允许执行一次。

### 5.5 加工收款

加工单支持 `DEPOSIT` 定金和 `BALANCE` 尾款两种收款类型。每次收款独立写入 `processing_payment` 和 `finance_record`，开单只形成应收，不计入收入。

## 6. 离线策略

### 6.1 允许离线

- 首页和报表缓存读取。
- 商品、会员、金价和旧料类型的只读查询。
- 未提交开单草稿。

### 6.2 必须在线

- 支付、退款、回收结算。
- 库存入库、出库、盘点审批调整。
- 交班确认。
- 会员余额变更和其他会产生财务流水的操作。

写操作统一携带 `clientRequestId`，服务端使用门店加请求号做幂等约束。网络恢复时不得自动重放支付、退款和库存调整，需展示失败原因并由操作员确认。

移动端在线状态由 `navigator.onLine` 与 `GET /actuator/health` 双重判断，3 秒一次心跳；WebSocket 断线只触发状态变化和数据刷新，不作为交易成功依据。

## 7. WebSocket 契约

当前连接地址为 `ws(s)://{host}/ws?token={JWT}`。消息统一采用：

```json
{
  "type": "ORDER_COMPLETED",
  "data": {},
  "occurredAt": "2026-09-09T10:00:00Z"
}
```

当前已使用事件包括 `GOLD_PRICE_UPDATED`、`APPROVAL_CREATED`、`APPROVAL_DECIDED`、`ORDER_COMPLETED`、`RECYCLE_COMPLETED` 和 `PROCESSING_ORDER_UPDATED`。后续增加事件时必须定义唯一事件名、门店范围、数据结构和重复处理方式。重连后以接口全量刷新为准，不依赖补发历史消息。

## 8. 开发验收门槛

### P0 接口与权限

1. 登录成功后不同角色只能访问对应接口，越权请求返回 403。
2. 会员新增、编辑、详情和生日筛选前后端字段均为 `YYYY-MM-DD`。
3. 商品按一级、二级分类筛选结果与库存分类一致。
4. 金价、旧料类型修改后，管理端和移动端读取同一接口结果。
5. 订单、支付、交班、库存写操作重复提交只产生一条业务记录。

### P1 数据一致性

1. 销售毛利使用订单项成本快照，修改商品成本不影响历史订单。
2. 盘点审批通过后商品库存、库存流水和审批状态一致。
3. 加工定金、尾款分别进入财务流水，收入合计与支付明细一致。
4. 门店切换或不同门店账号不能读取其他门店数据。

### P2 体验与恢复

1. 后端停止后 3 秒内显示离线，恢复后恢复在线。
2. WebSocket 断线后页面仍可通过接口刷新到最新数据。
3. 空列表、接口错误、权限错误和网络恢复均有明确提示。
4. 关键列表使用服务端分页、排序和筛选，前端不依赖全量数据。

## 9. 开发顺序与停线条件

1. 先冻结接口契约和响应示例，再实现页面。
2. 先补状态机和幂等测试，再接入支付、库存和审批写操作。
3. 每个模块完成后同时验证接口、数据库流水、权限和前端展示。
4. 发现文档路径与 Controller 不一致时，以实际 Controller 为准并回写接口文档。
5. 以下事项确认前暂停大规模功能开发：最终 Tab 数量、门店切换权限、离线写入边界、报表统计口径、加工/回收/以旧换新取消和退款规则。
