## 问题 9（跨端·时区）：移动端开单转到收银端后，时间**提前了 8 小时**

### 现象
手机端开的加工单转到收银端（前台待办 → 待确认加工 → **转交时间**列），显示时间比实际开单时间**早好几个小时**；手机端自己看时间又是**对的**，两边对不上。

### 已定位根因（运维已核实，证据如下，**不要再花时间猜**）
生产环境实测（2026-10-09 18:47 北京时间）：

| 对照项 | 实测值 | 结论 |
|---|---|---|
| 服务器系统时间 | `2026-10-09 18:47:58 CST (+0800)` | 宿主机是 +08 ✓ |
| **后端容器时间** | `2026-10-09 10:47:58 UTC (+0000)` | **容器未设时区 → 跑在 UTC** ✗ |
| **MySQL `now()`** | `2026-10-09 10:47:58` | **写入库的时间是 UTC** ✗ |
| MySQL `utc_timestamp()` | `2026-10-09 10:47:58` | 与 `now()` 相同 → 库确实是 UTC ✗ |

**因此**：服务端 `now()` 写入的 `create_time` 等字段全部比真实北京时间**早 8 小时**。
- 手机端 `dateTime()` 把库里的值当 UTC → 补 `Z` + 转 `Asia/Shanghai` → **显示反而是对的**（阴差阳错）；
- 收银端「转交时间」直接渲染库中原值 → **早 8 小时** ✗ ← 老板看到的问题；
- 同理，报表/统计里用 `curdate()`、`date(create_time)` 的"今天/本月"边界，在北京时间 00:00–08:00 之间会**算成前一天** ✗。

### 修复策略（**时区配置与历史数据校正由运维执行；Codex 不要动 compose / DB 配置**）
- **运维侧（老板的部署流程）**：后端容器加 `TZ=Asia/Shanghai`、MySQL 设 `--default-time-zone='+08:00'`（新写入即为北京时间）；随后对历史时间列做**一次性 +8 小时校正**（先备份、可回滚）。
- **代码侧（Codex 做）**：
  1. **界面不要再做时区加减**：时间统一"**库里是什么就显示什么**"，全端共用一个格式化函数（`YYYY-MM-DD HH:mm`）；
  2. 手机端现有 `dateTime()` / `fmtTime()` 里的 `+ 'Z'` + `Asia/Shanghai` 转换在时区修正后要**去掉**（否则会**多 +8 小时** ✗）→ 统一改为原样显示；
  3. 统计/报表的日期边界统一按 `Asia/Shanghai` 计算（库侧统一后直接用本地日期即可）；
  4. 打印模板（工单/质保单/小票）的"创建时间/打印时间"同样统一口径。
- **验收**：
  1. 手机端开单 → 收银端「转交时间」与手机时间**一致**，且等于实际开单时刻（±1 分钟）；
  2. 工单/质保单打印的"创建时间/打印时间"与之一致；
  3. 北京时间 08:00 前后各下一次单，报表"今日"数字都对；
  4. 手机端 / 收银端 / 管理端 / 打印，四处显示**完全相同**。
