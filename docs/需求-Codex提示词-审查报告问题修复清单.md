## 一、优先级最高（当天可完成，都跟钱/规则直接相关）

### 1. 交班现金统计仍写死 `CASH`（生产现金渠道是 `XIANJIN`）★ 最要紧

- **现状（已核实为真）**：后端 `ShiftController.java:33` 与 `:61` 的 SQL 都是 `… and pay_method='CASH' …`，而**生产门店现金渠道的 code 是 `XIANJIN`** → 交班"系统现金"会算少、甚至为 0。
- **期望**：按**门店渠道语义**识别现金渠道（参考 `PaymentChannelPolicy` / 手机端已有的按名称匹配实现），**禁止写死 code**；收银端/手机端的交班显示与后端统计用同一口径。
- **验收**：本地用 `CASH` 渠道、以及把门店渠道改成 `XIANJIN` 两种配置各录一笔同额收款，交班金额必须一致；四套测试全绿。

### 2. 超额旧金返款没挡"储值"渠道

- **现状（已核实为真）**：`PayController.java:190` 的 `resolveOldMaterialPayoutMethod(...)` 只拒绝字面值 `"BALANCE"`；生产用的 `CHUZHI` 等储值渠道会被放过（该文件内 `isBalanceChannel` 只用了 1 处）。
- **期望**：改用 `PaymentChannelPolicy.isBalanceChannel(db, storeId, method)` 语义识别并拒绝储值作为返款方式；错误提示要说明"储值不能作为返款方式"。
- **验收**：以启用的 `CHUZHI` 提交超额返款 → 请求被拒、会员余额与财务流水均无变化；以 `XIANJIN` 提交 → 正常记账。
- **同类自查**：全仓再搜一遍做**业务判断**的 `"BALANCE"` / `"CASH"` / `"WECHAT"` 字面量（不只是展示文案），一并改成语义识别。

### 3. 足金线规则还有两处漏算（0.995 及以上应按整克）

- **现状（已核实为真）**：
  - `StockController.java:688`：`weight*purity*coalesce(direction,1) effective_weight`（SQL 里乘成色）；
  - `ProcessingController.java:989`：`round(coalesce(o.old_gold_weight,0)*coalesce(o.old_gold_fineness,1),3) incoming_net_weight`。
- **期望**：统一走 `Fineness` / `finenessFactor`（成色 ≥0.995 记整克），**不要在各处 SQL 里重复实现**；改完把这两处的展示/统计口径与 `Fineness.weight` 对齐。
- **验收**：以成色 0.999 与 0.994 各一条数据，核对库存旧料明细与损耗订单的有效克重；补/改单测（区分 0.995 临界值）。

### 4. 手机端还有一个"手填返款方式"的入口

- **现状（已核实为真）**：`mobile/src/views/PendingTasks.vue:102-107` 仍用 `window.prompt` 让店员手敲金额与 `CASH/WECHAT/ALIPAY` 这类英文 code。

### 5. 离线草稿：超 50 条会静默丢失 + 永久错误无限重试

- **现状（已核实为真）**：`mobile/src/utils/pendingProcessing.js`：`MAX_ROWS=50`，写入用 `rows.slice(0, MAX_ROWS)` → 超出部分被**静默丢弃**；`mobile/src/utils/processingSync.js:39-50` 补传失败只累加 `tries`，没有停止策略、没有失败原因、没有人工处理入口。

## 二、需要设计/测试的第二批

### 6. 组合支付：撤回/退款要按"支付组成"逐笔冲销

- **现状（已核实为真）**：组合支付只落**一条** `pay_method='COMBINATION'` 的收款与财务流水，`components` 仅用于生成备注；撤回时也按汇总方式冲销 → **无法按现金/微信/团购逐项核销、对账**；团购核销号存在主单字段并有唯一约束，**撤回时没有释放/标记凭证状态**。
- **期望**：把组合支付拆成**可查询、可逆**的子流水（例如 `processing_payment` 里按方式各存一条，或用明确的子表），撤回/退款/报表/交班按组成分别冲销；并明确**团购凭证撤回后的占用规则**（释放 or 标记作废）。
- **验收**：用「团购 + 现金」支付一单 → 依次核对：收款明细、撤回/退款的反向流水、团购凭证能否再次使用、报表与交班汇总是否对得上；补单测。

### 7. 有促销优惠时返款口径不对

- **现状（已核实为真）**：`ProcessingController.java:1380-1384` / `673-677`：`due = grossDue - promotionDiscount`，但返款用 `grossDue - paid` 的正差额；称重路径同样用 `billingGrossDue` 而非优惠后应收 → **可能多退钱给客户**。
- **期望**：返款一律按**扣除促销后的最终应收**计算，并与返款审批阈值、返款登记接口同一口径。
- **验收**：优惠前应收 100、优惠 20、已收 90 → 返款应为 **10**；再测称重后重算的场景；补单测。

### 8. 加工开单幂等：并发会 500、空 key 可重复建单

- **现状（已核实为真）**：`ProcessingController.java:280-284`（预查询）+ `383`（插入）→ 两个请求**同时**到达时都会"查不到"，后者撞唯一键并**返回 500**；请求不带键时以 `NULL` 保存，唯一索引允许多条 `NULL` → **可重复建单**。
- **期望**：以**数据库唯一键竞争**作为原子保障：捕获 `DuplicateKeyException` 后按（门店 + clientRequestId）**读取并返回原单**（幂等回放，不是 500）；**写接口要求非空 key**（为空则拒绝并提示客户端升级/重试）。
- **验收**：并发提交同一键（本地用两次并行请求）、空键提交、断网重传 → 同一键只产生一单且**不返回 500**。

### 9. 幂等键"先占后退"的事务边界（需实测确认）

- **现状（待实测）**：`ProcessingController.java:575-578`、`1117-1126`（同类还有 `store-gold`、`notify`）：先写幂等操作日志 `claimProcessingWrite(...)`，再做状态/业务校验。若某个异常路径被吞并提交，重试同一 key 会被当作**假成功回放**。
- **期望**：逐条核对每个 claim 路径——**失败必须回滚、不占键**；幂等记录与成功结果**原子提交**；重放时校验 key 与订单/操作类型一致。
- **验收**：对"已取货"的单重复提交称重、对不可流转状态重复提交状态变更 → 每次都应返回原业务错误，**不能出现假成功**。
