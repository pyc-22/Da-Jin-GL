## 1. 客户照片不用登录就能看 **[已确认]**

- **现状**：系统存客户照片用的是公开网址。**别人只要拿到那个网址，不登录也能打开**（电脑、手机浏览器直接输入就能看）。手机端、收银端上传的照片都属于这类。
- **会怎么样**：客户的照片（首饰、证件、单据）可能被外面的人看到。
- **期望**：能看到就能看到，重点是别人能否直接修改数据，如果不能就暂时不用管
- 技术细节：`AuthInterceptor.java:17` 把 `/api/file/` 整个前缀设为免登录；业务代码按该前缀存照片（`ProcessingController.java:740、1662`）。

## 2. 新员工的默认密码是 `admin` **[已确认]**

- **现状**：在管理端"员工管理"里新增员工时，**如果没填密码，系统就给他设成 `admin`**；而且密码在数据库里是**明文**存放的（不是加密的）。
- **会怎么样**：随便谁都能猜到新账号的密码，登进去能看到全店的数据（客户、单据、金额）。
- **期望**：我记得在管理端不填密码是不予创建账号的，核查一下
- 技术细节：`AdminController.java:173`（`getOrDefault("password","admin")`）；登录时对非 `$2` 开头的口令走明文比对。

## 3. 回收开单"点两次"可能开出两张单 **[已确认]**

- **现状**：手机或收银端点"提交"时，如果**网络卡住、店员又点了一次**，系统是靠"先查一下有没有提交过"来判断的——**没有数据库层面的唯一约束兜底**。两个请求同时到达时，两边都"查不到"，于是各插一张单。
- **会怎么样**：同一笔回收金子被记两次，钱和库存都对不上。
- **期望**：希望网络即使卡顿，**店员又点了一次也不会出现单据重复问题**
- 技术细节：`RecycleController.java:31-33`（用 `operation_log` + `clientRequestId` 先查后插，回收单本身没有唯一键）。

## 4. 回收价格由手机传过来，服务器没核对 **[已确认]**

- **现状**：回收单的价格是**手机端算好、随请求一起传上来的**（不传才用当天价）。服务器**没有**检查这个价跟今天的行情差多少、有没有超出合理区间。
- **会怎么样**：懂技术的人改一下手机请求，就能**自己定回收价**。
- **期望**：这个暂时不用管，此系统为内部使用
- 技术细节：`RecycleController.java:37`（`price = q.get("recyclePrice")`）、`:45`（用该价算金额）。

## 5. 单号可能重复 **[已确认]**

- **现状**：好几处单号是用「**类型 + 当前毫秒数**」拼出来的。一毫秒内发生两笔同类操作，就会拼出**一模一样的单号**。
- **会怎么样**：两张不同的单拿到同一个号，查单、对账、打印都会乱。
- **期望**：先回答发生的概率为多少
- 技术细节：`RecycleController.java:48`、`StockController.java:120`、`StockController.java:521`、`ShiftController.java:72`。

## 6. 商品成本价填 0，出库就"永远不用审批" **[已确认]**

- **现状**：出库要不要走审批，是按「**成本价 × 出库数量**」算出来的金额跟门槛（默认 1 万）比。如果商品成本价是 0（按克商品经常忘填——生产上「足金用料」之前就是 0 和填错两种都有），算出来永远是 0，**怎么出库都不会触发审批**。
- **会怎么样**：贵重金料出库没人把关。
- **期望**：这个暂时没事，目前管理员只有老板
- 技术细节：`StockController.java:534-536`（`value = coalesce(cost_price,0)*qty` 与 `stock_out_approval_limit` 比较）。

## 7. 入库重复提交会"报错"而不是"自动跳过" **[已确认]**

- **现状**：同一批入库如果因为断网被重发，一般能认出来并跳过；但如果**两次几乎同时到达**，唯一约束会撞车 —— 而现有代码只捕获了"单件码重复"，所以会**直接报错**（提示"单件码已登记，不可重复入库"），而不是安静地返回原来那张单。
- **会怎么样**：店员看到报错，不知道其实已经入库成功了，容易重复操作。
- **期望**：那报错改为当前已执行加解释
- 技术细节：`StockController.java:160`（预检）、`:201`（插入）、`:278`（仅捕获单件码冲突）。

## 10. 时间比北京时间慢 8 小时 **[已确认]**

- **现状**：服务器和数据库的时间跑在 UTC（世界标准时间），**比北京时间慢 8 小时**。
  - 手机端自己加了 8 小时 → 看着"是对的"；
  - **收银端直接显示数据库时间 → 比实际早 8 小时**（你上次说的"移动端开单转收银端时间对不上"就是这个）；
  - 报表的"今天/本月"在**早上 8 点之前**会把昨天的单算进今天。
- **会怎么样**：跨端时间不一致、日报/月报边界错一单。
- **期望**：时间对齐，且正确
- 技术细节：生产实测（服务器 `18:47 CST`／后端容器 `10:47 UTC`／MySQL `now()` = `utc_timestamp()`）。

## 12. 按克商品的"成本价"没写单位，库存金额能差 50 倍 **[已确认]**

- **现状**：管理端填商品成本价时，**界面上没写单位**。库存金额是「库存 × 成本价」算的，而**按克商品的库存单位是"克"** → 如果成本价按"整件 50 克"填（生产上「足金用料」填了 45500），金额就被放大几十倍。
  - 实例：48.67 克 → 显示 **¥2,214,485**（已人工修正为 940 元/克 → **¥45,749.80**）
  - 反过来也有人填 0 → 2500 克在库算成 **¥0**
- **会怎么样**：库存金额（资产）对不上；两头错还会互相抵消，看不出问题。
- **期望**：按克算的是克重×每克价格，卖给客户也是按克卖的不看件数
- 技术细节：`AdminController.java:143-144`（`sum(g.stock*g.cost_price)`）。
