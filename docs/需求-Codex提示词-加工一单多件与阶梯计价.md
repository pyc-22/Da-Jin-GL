## 2. 需求 A：一张加工单支持多件 / 多项目

### 现状

`processing_order` 是「1 单 1 项目」：`processing_item_id / item_name_snapshot / quantity / pricing_unit(按件|按克) / unit_labor_fee / labor_fee / billing_weight`，加上来料 `old_gold_weight/old_gold_fineness`、补金 `store_gold_*`、称重 `finished_weight/finished_fineness/recovered_weight/melt_weight`、应收/优惠/收款/取货/提成。

### 目标

客户带来 **40g 来料**，要加工**好几件不同首饰**（不同项目、不同数量、可能不同计价方式）：**一张单开出来、一起称重、一起结算、一起打印**。

**同时，只加工一件的普通单子必须和今天一样快、一样简单。** 也就是：**不区分"单项目模型 / 多项目模型"，统一按「1 个子项 … N 个子项」实现**：

- **单项目单 = 多项目单的特例（子项数 = 1）**，不存在两种模型、不需要任何"转换"概念；
- 开单界面**默认就是 1 行**（和现在操作步骤完全一致），需要多件时点「＋ 添加项目」加行；
- 老单（升级前只有主表字段的）**读取时自动视为 1 个子项**，可编辑、可打印，**保存后自然成为 1 个子项的单**——没有弹窗确认、没有只读限制、没有"首次转换"的特殊状态；
- 主表汇总字段（`labor_fee` 工费合计、`item_count` 件数）**持续同步**，列表/报表/提成/打印模板全部沿用。

### 必须覆盖

1. **数据模型**：新增子项表 `processing_order_item`
   `order_item_id, store_id, processing_order_id, processing_item_id, item_name_snapshot, quantity, pricing_unit, unit_labor_fee(单价快照), billing_weight(计费克重), labor_fee(工费), remark, sort`
   `processing_order` 保留汇总：`labor_fee` = 子项工费合计，并新增 `item_count`（件数合计，列表/打印用）。
   保存时**保证至少 1 个子项**（单项目单也写 1 行）；子项数上限建议 20。
2. **老数据兼容（已定：自动单项兼容，Codex 不要再问）**：
   - 已存在的单视为「1 个子项」；**详情/打印读取时若无子项，自动回退读主表字段**（照常显示、照常打印）；
   - **首次编辑保存时**，系统用旧字段**自动合成 1 个子项**，此后该单走新模型（单向但无损：来料、补金、成品称重、应收、收款记录原样保留）；
   - **不弹"是否转换"确认框、不禁止编辑老单**；
   - 写入时**持续同步主表汇总字段**（`labor_fee` 工费合计、`item_count` 件数），保证列表/报表/提成/打印模板全部兼容；
   - 只有子项与主表字段都为空的数据才拒绝编辑并提示。
3. **来料与补金：整单共用**（一张单一份 40g 来料与补金）；**成品整单称一次**（不做逐件称重/逐件损耗）→ 沿用 `processing_order` 现有 `old_gold_*` / `store_gold_*` / `finished_weight` 等字段。
   ⚠️ 但**按克子项必须有自己的"计费克重"**（工费 = 单价 × 克重，不填就算不出钱）：完工时**逐项录入每个按克子项的计费克重，合计不得超过整单成品实重**；**只有一个按克子项时默认带出整单成品实重**（门店日常操作步骤不变）。按件子项不需要克重。
   这与"整单称一次"不矛盾：**称重/损耗/补金仍按整单算**，只是按克子项各自记一个计费克重（可以按成品标签或实际量一下，不需要单独走称重流程）。
4. **计价**：每个子项按自己的 `pricing_unit` 算工费（按件 = 单价 × 数量；按克 = 单价 × 计费总克重，见需求 B）；应收 = 工费合计 + 补金金额 − 回收屑抵扣 − 优惠（下限 0）。
5. **收银端**（`front-pc/src/App.vue` 加工开单 / 称重 / 结算 / 收款 / 取货）：
   开单支持「+ 添加项目」多行（项目、数量、按件/按克、单价、备注）；称重与完工按确认的方案；收款、打印、取货流程保持现在的体验。
6. **手机端**（`mobile/src/views/ProcessingOrders.vue`）与**管理端**（`admin-web/src/views/Processing.vue`）：开单、详情、称重都能看到并编辑多个子项；列表显示「N 件」。
7. **打印**：工单 `GET /api/processing/orders/{id}/print` 与质保单 `/warranty` 都要**逐项打印**（项目 / 数量 / 计价方式 / 单价 / 工费）并给合计。
8. **报表与提成**：加工单数按「单」统计、件数按「件」统计；提成基数仍按整单工费（复用 `ProcessingAmounts.laborBase`，不要改口径）。
9. **幂等与撤回**：整单一个 `client_request_id`；撤回时子项、库存、流水、提成一起冲销，不留半截数据。
10. **边界**：子项为空 / 数量 ≤ 0 / 单价为 0 / 合计为 0 的校验；老单再编辑；并发提交。

## 3. 需求 B：按克项目阶梯计价

### 现状

按克项目：工费 = `unit_labor_fee(元/克)` × `billing_weight(计费总克重)`；计费总克重在**完工称重**时填写（默认带出成品实重）。

### 目标（老板原话）

「10 克以下每克多少元（或者 N 克以下直接 X 元），10 克以上多少元一克」。例如：

- ≤10g → **30 元/克**；>10g → **25 元/克**
- 或 **≤5g 直接一口价 150 元**

### 必须覆盖

1. **配置入口**：管理端「加工项目」里为每个按克项目配置阶梯规则。推荐：
   - 项目上增加 **计费算法** 字段 `price_calc_mode`（`WHOLE_TIER` 全额按档 / `PROGRESSIVE` 累进分段）——**两种都要支持，按项目（按门店）各自选择**；
   - 新表 `processing_price_tier(tier_id, store_id, item_id, min_weight, max_weight(NULL=不限), mode(PER_GRAM 每克价 | FLAT 一口价), price, sort, status)`；
   要能增删改、排序、启停；与项目一起导出/迁移。
2. **两种算法都要实现，并按项目配置**：
   - **全额按档 WHOLE_TIER**：整单（或该子项）计费克重落在哪一档，就整笔按该档单价/一口价计算。
   - **累进分段 PROGRESSIVE**：按档位从低到高**分段**累加；因此这套档位必须满足：最底档从 0 起、档位**首尾相接不重叠**、最高档不限上限；每段金额 = 该段克重 × 该段单价（允许某段是 `FLAT` 一口价，则命中该段时该段直接取一口价）。
   - 两种模式下都：金额 2 位小数 HALF_UP；克重 3 位小数；**恰好等于临界值**归入「≤该值」的档（即区间取闭区间的上端，例如 10.000g 归 ≤10g 档）；`FLAT` 与 `PER_GRAM` 同时命中时 **`FLAT` 优先**（更具体）。
   - 配置界面对 `WHOLE_TIER` 允许档位留空档（只校验不重叠）；对 `PROGRESSIVE` 必须校验**连续无空洞、无重叠**，否则保存报错并指出问题档位。
3. **计算唯一入口**：后端提供唯一工费函数（如 `ProcessingPricing.laborFee(item, billingWeight)`），三端共用同一规则与提示文案；无匹配档位时回退项目单价 `unit_labor_fee`。
4. **影响面（都要同步）**：开单时的工费参考/预估 → 完工称重的工费重算 → 应收重算 → 优惠（低于折扣阈值要进审批）→ 打印（单据上显示命中档位，如「按克 25.00 元/克 × 12.345g = 308.63」）→ 报表（工费口径不变）→ 撤回/退款冲销 → 提成基数（沿用整单工费）。
5. **一致性**：计费总克重变化后，工费与应收必须同步重算（复用现有 `weighing` 重算逻辑），**不允许小票金额与库中金额不一致**。
6. **测试**：档位命中 / 边界 / 无匹配回退 / 一口价 / 精度 / 撤回后不重复计提成；本地端到端造单验证。

## 6. 老板已确认的口径（Codex 按此实现，不要再猜）

1. **来料与补金：整单共用**（一张单一份 40g 来料与补金）；**成品整单称一次**，不做逐件称重/逐件损耗。
   → 沿用 `processing_order` 现有的 `old_gold_*` / `store_gold_*` / `finished_weight` 等字段。
1.1 **多按克子项的计费克重：逐项分配**（对应 Codex 追问选「1 逐项分配（推荐）」）：
   - 完工时**逐项录入每个按克子项的计费克重**，**合计不得超过整单成品实重**；
   - **只有一个按克子项时默认带出整单成品实重**（日常单件操作不增加步骤）；
   - 按件子项不需要克重；
   - 这是"计费克重"，不是逐件称重：**称重/损耗/补金仍按整单计算**。
2. **混搭允许**：同一张单里可以既有「按件」子项、也有「按克」子项；**折扣审批按整单**判定（沿用现有整单折扣阈值逻辑）。
3. **阶梯规则按门店保存**（规则表带 `store_id`，连锁时各店可不同价；当前是单店）。
4. **小票/单据要印价格说明**（例如「按克：10g 以上 25.00 元/克」），并显示本单命中档位与单价。
5. **临界值不是写死的 10 克**：档位可任意增删（例如 5 / 10 / 20 / 50 克都行），每档可选「每克价」或「一口价」；档位表要能排序与启停。
6. **阶梯算法：两种都要，按项目配置**（`WHOLE_TIER` 全额按档 / `PROGRESSIVE` 累进分段），不是二选一；配置界面按所选算法做对应校验（见第 3 节第 2 条）。
7. **老单编辑：自动单项兼容**（详情回退读主表 → 首次编辑自动合成 1 个子项 → 保存后走新模型；**不弹"是否转换"确认、不禁止编辑**；主表汇总字段持续同步）。即 Codex 追问的三个选项选 **「1 自动单项兼容（推荐）」**。

## 7. 阶梯两种算法示例（用真实数字，方便老板拍板）

假设档位：**≤10g → 30 元/克**；**>10g → 25 元/克**。某个成品称重 **12.345g**：

| 算法（按项目配置） | 计算 | 工费 |
|---|---|---|
| **全额按档 WHOLE_TIER** | 12.345g 落在「>10g」档 → 整笔按 25 元/克：12.345 × 25 | **308.63 元** |
| **累进分段 PROGRESSIVE** | 前 10g × 30 = 300.00；超出 2.345g × 25 = 58.63 | **358.63 元** |

**两种都要实现，按项目（门店）各自选择**：有的项目老板想"量大整笔便宜"（全额按档），有的项目想"前几克保护价"（累进分段）。
一口价档位（如「≤5g 直接 150 元」）在两种算法下都支持：全额按档时整笔取 150 元；累进分段时该段直接计 150 元。
累进分段的档位必须**从 0 开始、首尾相接、最高档不限上限**，保存时校验无空洞无重叠。

## 8. 原待确认清单（已由老板答复，保留备查）

1. 一单多件时：**整单共用来料与补金**；成品**整单称一次**，不逐件称重。
2. 多件可以**混搭**按件/按克；折扣审批**按整单**。
3. 阶梯**按门店配置**（规则带 store_id）。
4. 小票**要印价格说明**。
5. 阶梯**两种算法都要**（全额按档 / 累进分段），**按项目配置**，不是二选一；小票印价格说明。
