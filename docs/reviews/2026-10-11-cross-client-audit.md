### P1 — 孤立的加工返款审批在详情接口触发 HTTP 500

- **位置**：
  - `backend/src/main/java/com/dajin/system/approval/ApprovalController.java:46-61`
  - 同文件 `:95-113,198-212`
  - `backend/src/main/java/com/dajin/system/common/DbSupport.java:14-16`
  - `mobile/src/views/RoleHome.vue:208`
  - `admin-web/src/views/Approval.vue:36-39,41-58`
- **复现**：本地只读请求 `GET /api/approval/62` 返回 HTTP 500、业务码 `500000`；`GET /api/processing/orders/91` 返回 HTTP 200、业务码 `404701`（加工单不存在）。对照 `GET /api/approval/61` 返回 HTTP 200。健康检查 `GET /actuator/health` 为 `UP`。
- **根因与证据**：详情方法查询审批后，用 `db.one(...)` 读取其关联加工单；`DbSupport.one` 使用 `queryForMap`，零行会抛 `EmptyResultDataAccessException`。该异常没有被转换成业务错误，最终由全局异常处理器包装为 `500000`。审批通过/驳回也会进入 `decideProcessingRefund()`，其 `for update` 查询同样使用 `db.one`；关联单缺失会在审批处理时再次抛错。处理端方法带事务，异常会回滚本次审批状态更新，但用户仍只看到服务器错误。
- **跨端影响**：移动端 `openApprovalDetail` 捕获错误并弹出 Axios 消息；管理端详情及审批动作也先请求详情，因此同一坏记录会阻塞这些入口。
- **孤立成因**：`approval.biz_id` 是多业务类型关联列，schema 未设加工单外键；源码中未找到删除 `processing_order` 主表记录的应用 SQL。当前证据可以证明数据孤立，尚不能确定它由人工清理、数据恢复/导入或其他外部操作造成。
- **建议**：详情读取关联单时显式处理缺失并返回稳定的业务错误/“关联单据不存在”数据，不返回 500；审批处理前检查关联单并明确允许或禁止对孤立审批作废/驳回，校验应在状态更新之前。增加孤立关联的详情、通过、驳回测试，并提供只读孤立审批巡检 SQL；先盘点再人工决定历史记录处置，不自动删除。
- **验证结果**：本地运行态已复现详情 500；未对该记录执行审批写操作。

### P1 — 交班重试使用新幂等键，双击或响应丢失后可连续轮转班次

- **位置**：
  - `front-pc/src/App.vue:1881-1920`，交班按钮在 `:2105` 附近
  - `mobile/src/views/Shift.vue:95-108`
  - `backend/src/main/java/com/dajin/system/shift/ShiftController.java:99-147`
- **复现条件**：前台收银端重复点击“确认交班”，或交班已在服务器提交但响应丢失，随后用户再次提交；移动端在一次失败后重试。各次提交会生成不同 `clientRequestId`，服务器视为不同交班并调用 `shifts.rotate()`。
- **证据**：收银端在每次 `confirmShift()` 调用里生成 `uuid()`，交班按钮没有提交中禁用状态；移动端每次调用用 `shift-${Date.now()}`，失败后 `finally` 会恢复按钮。后端只对收到的同一非空 key 去重；key 缺失时还会生成随机 `SHIFT-...` 键，无法识别请求重放。轮转班次和交班日志都处于事务中，但事务不能识别用户用新 key 发起的第二个业务请求。
- **影响**：一个实际交班可能生成多个交班日志并连续切换班次，后续收款归属到错误班次，造成班次对账与报表分界偏移。
- **建议**：交班表单在整个成功/失败重试周期内复用固定 request id，只有确认完成后才换新 ID；按钮增加提交锁。服务器将 key 设为必填并校验长度；对相同 key 返回原交班结果，对不同 key 的并发操作使用门店级行锁/当前班次版本校验避免重复轮转。覆盖相同 key 重放、双击、提交成功但响应丢失后的重试和缺失 key 测试。
- **验证结果**：由源码调用链确认，未在本地触发真实班次写操作。

### P1 — 收银端回收单每次点击生成新 key，重复点击可重复建单并登记支出

- **位置**：
  - `front-pc/src/App.vue:1725-1729,2180`
  - `backend/src/main/java/com/dajin/system/recycle/RecycleController.java:29-63`
  - `db/schema.sql:51`
- **复现条件**：收银员快速连续点击“保存回收单”，或首次写入已成功但客户端未收到响应，之后再次点击。
- **证据**：`saveRecycle()` 每次调用都生成新的 `uuid()`，保存按钮没有 busy/disabled 防连点。后端仅在 key 非空时查询和写入 `operation_log`；key 为空时完全跳过重放记录。前端即使对相同 key 重放，后端也只返回 `{idempotentReplay:true}`，不返回原回收单号、金额、状态或审批信息。
- **影响**：不同 key 会创建多张回收单，并可能重复生成旧料记录、审批及财务支出；相同 key 的重放也无法让客户端恢复原结果。移动端 `RecycleCreate.vue` 已为一份草稿保留 `activeRef`，但收银端路径没有该保护。
- **建议**：收银端在一次回收表单生命周期内保存并复用同一 request id；添加提交中锁。后端要求非空、限长 key，并将幂等结果绑定到回收单返回完整原结果；保持业务数据与幂等记录原子提交。覆盖双击、相同 key 重放、无 key 拒绝、审批单重放和财务/旧料记录只生成一次。
- **验证结果**：由源码确认风险路径，未创建本地回收业务数据。

### P2 — 改密长度按字符限制，未限制 BCrypt 的 UTF-8 字节长度

- **位置**：`backend/src/main/java/com/dajin/system/auth/AuthController.java:14-15,47-57`
- **复现条件**：设置含多字节字符的新密码，字符数不超过 72、UTF-8 编码长度超过 72 字节。
- **证据**：请求 DTO 的 `@Size(max=72)` 和正则 `.{8,72}` 都按字符约束；随后直接传给 BCrypt。对当前工作区依赖做过本地临时验证：32 个字符、80 个 UTF-8 字节的输入会通过当前长度规则；变化发生在 BCrypt 72 字节截断位置之后的后缀，仍匹配相同哈希。
- **影响**：用户以为密码后缀参与认证，但实际不参与；不同密码可能等价，且可能产生账号恢复/支持歧义。
- **建议**：优先采用不会截断输入的现代密码哈希策略并为旧哈希设计迁移；若继续使用 BCrypt，服务端在编码后按字节数限制并明确拒绝超限输入，而非只按字符数检查。补充 ASCII、多字节恰好 72 字节及超过 72 字节测试。
- **验证结果**：静态代码检查和本地临时 BCrypt 验证；没有修改账号或数据库。

### P2 — 加工照片 URL 把 JWT 放入查询参数，可能进入代理/访问日志

- **位置**：
  - `front-pc/src/App.vue:377-383`
  - `mobile/src/views/ProcessingOrders.vue:249-255`
  - `admin-web/src/views/Processing.vue:119-127`
  - `backend/src/main/java/com/dajin/system/upload/FileController.java:40-55,63-90`
- **复现条件**：三端渲染加工照片时，将会话 token 添加到 `access_token` 查询参数，以便图片元素携带认证信息。
- **证据**：三个客户端的照片 URL helper 都会追加完整 JWT；后端从 `Authorization` 或 `access_token` 读取 token。照片鉴权的门店和角色归属查询已按管理员/经理/收银员本店、销售创建人或归属销售、师傅派单人分别约束，并返回 `private` 缓存头；这些权限规则没有发现跨店查询缺口。
- **影响**：短时有效的 bearer token 会随图片请求 URL 传输，可能出现在代理 access log、错误追踪或浏览器资源诊断记录中；访问日志读取者可能在 token 过期前复用该令牌。
- **建议**：优先用带 Authorization 的 fetch 获取照片 Blob/object URL，或使用极短时、单对象、只读签名 URL；同时确保代理和错误监控对 `access_token` 做脱敏，设置严格的 `Referrer-Policy`。不要把长期会话 JWT 继续作为图片查询参数。
- **验证结果**：源码确认；`FileControllerPhotoAccessTests` 覆盖未登录拒绝、销售归属、收银员本店范围、师傅派单范围。未进行代理日志泄露测试。

- **三端调用链参数**：移动端 `RoleHome.vue`、管理端 `Approval.vue` 及收银端待办/审批刷新均使用审批 ID 调用同一详情接口；收银端加工收款、返款、取货和照片请求均携带请求编号，响应按现有 `ApiResponse.data` 结构读取。未看到三端把加工返款审批误当成销售审批的路径分叉。
- **收银端照片/取货**：`processing-pickup.js` 先执行尾款与返款余额校验，有照片才上传照片，随后再提交 `PICKED_UP` 状态；无照片时不会发送空照片请求。对应 helper 测试覆盖无照片和有照片两种分支。

- **销售收款**：`PayController.pay` 校验 `clientRequestId` 非空，读取销售单时使用 `select ... for update`；与既定收款并发保护相符。
- **加工写路径**：加工开单要求非空且限长的 `clientRequestId`，schema 有 `(store_id, client_request_id)` 唯一键；与销售/回收相比，其 key 合同更完整。此前端到端生产部署不在本次范围。
- **照片归属范围**：覆盖管理员、经理、收银员、销售、打金师傅的本店/订单归属规则；没有发现取货、称重、来料照片使用不同授权策略的证据，因为相同 `/processing/{orderNo}/...` URL 均通过同一校验函数。
- **测试覆盖说明**：现有审批权限测试覆盖审批权限、跨店/不存在审批单的写保护，但没有覆盖 `PROCESSING_REFUND` 的孤立加工单读写；这正是建议新增的回归覆盖点。
