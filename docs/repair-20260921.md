# Local repair checklist (2026-09-21)

Scope: repair the audit findings, add regression coverage, run backend tests and
front-pc build, then package locally. Do not deploy to the cloud server.

Implemented:
- Sales reservation is released on cancellation, while inventory is deducted only after successful payment.
- Payment and cancellation are idempotent; duplicate payment cannot debit the member or create a second stock-out ledger.
- Last-item reservation is serialized so two orders cannot reserve the same single item.
- Tracked piece status is restored on cancellation and updated on sale/refund.
- Cashier settlement reuses a pending order and opens payment directly, preventing the page-jump/retry flow.
- Processing orders keep their `PROCESSING` status after confirmation and remain visible in the cashier/mobile lists.
- Refunded or non-pending orders cannot be paid; settlement must update successfully.
- Processing stored-value debit and order-locked replay checks.
- Goods price edits cannot overwrite inventory.
- Legacy staff role assignment and target authorization.
- Deductions require old-material details.
- Cashier processing list/detail access and stable error handling.
- Aggregate-only payment support and sales inventory ledger.
- Durable offline cancellation, server cancellation tombstone and request lock.
- Browser conflict handling and fallback queue synchronization.
- Handover checkout uses saved amounts.
- Split refund by original payment channels, current shift assignment and zero-cash return.
- Refund inventory ledger and returned old-material stock-out ledger.
- Manual stock-out and stock-count operations protect reserved stock and synchronize tracked pieces.
- Commission recalculation is idempotent and refunds reverse its commission.
- Per-gram processing billing uses billing weight; repeated gold returns each create a separate ledger entry.
- Standalone legacy trade-in settlement is rejected unless it goes through the normal goods sale/payment flow.
- Member recharge has an independent balance ledger, finance record and idempotency key; legacy consumption records remain readable.
- Follow-up tasks can be scheduled repeatedly without duplicate tasks on retries.
- Manual backup executes `mysqldump`, compresses the result, writes atomically and reports failures without leaving partial files.
- Upgrade compatibility migration preserves stock and member balances; interrupted follow-up index upgrades can resume without recreating the obsolete unique index.
- Both backend Dockerfiles include the MySQL client required by backups.

Functional impact:
- Stock becomes available again after cancellation; payment consumes the reservation exactly once, preventing overselling of the last item.
- Cashiers can enter payment on the first checkout click and continue locating confirmed processing orders.
- Refunds, stored-value payments/recharges, commissions and old-material movements retain consistent financial and stock ledgers on retries.
- Price edits, stock counts and manual outbound operations cannot silently consume stock reserved by another order.
- Recurring follow-up scheduling, schema upgrades and backups no longer fail in the covered legacy/retry scenarios.
